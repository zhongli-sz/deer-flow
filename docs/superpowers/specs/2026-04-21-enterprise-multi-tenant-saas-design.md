# DeerFlow 企业级多租户 SaaS 改造设计（逻辑隔离）

**日期**：2026-04-21  
**状态**：已评审（对话确认），待实现计划拆分  
**范围**：在共享基础设施上为多租户提供逻辑数据隔离；不强制物理每租户独立数据库实例，不强制 Postgres RLS。

---

## 1. 背景与目标

DeerFlow 2.x 当前以单租户/私有化部署为主：API 文档明确 **未内置应用层认证**；持久化涉及 LangGraph **checkpoint**、与 checkpointer 同配置的 **Store**、长期记忆、线程 **artifacts**、沙箱工作区及 Gateway/LangGraph 暴露的 HTTP 能力。  
本设计在 **不改动“多租户业务语义”的大前提** 下，将系统改造为可服务企业客户的 **SaaS 多租户形态**：每个租户的数据在访问控制与存储命名上 **均可独立归因**，跨租户读取在正常情况下不可达。

### 1.1 目标

- **租户隔离（逻辑）**：共享集群与共享（或分区）存储的前提下，所有持久化数据与可下载产物均可绑定到单一 `tenant_id`。  
- **身份与授权**：**OIDC JWT** 作为外部身份；**JWT 校验通过后再做服务端租户成员校验**，通过后写入请求级租户上下文。  
- **非数据库数据**：采用 **租户根隔离**（目录与对象键前缀 + 路径规范化与归属校验）。  
- **可运营**：审计、指标、配额/限流、测试门禁与分阶段上线策略可落地。

### 1.2 非目标

- 不强制 **Postgres RLS**（采用应用层强制 `tenant_id` 过滤为主）。  
- 不将 **每租户独立数据库实例** 作为本期必达交付（若未来需要，可作为独立升级项）。  
- 不默认解决 **第三方模型供应商侧** 的多租户合规与数据驻留（可作为补充策略与合同条款）。

### 1.3 关键假设

- SaaS 生产环境 **默认关闭匿名 API**；与“社区版可匿名”并存时，必须以 **配置明确的部署模式** 区分，避免误配。  
- 若 LangGraph Server 与 Gateway **进程分离**，必须定义 **内网信任边界**（mTLS 或短期内部令牌等），禁止 LangGraph 管理面对公网裸奔。  
- checkpoint/store 若共享底层表或文件，必须通过 **命名空间策略** 消除键空间碰撞与串读风险；禁止依赖“随机 thread_id 不碰撞”作为隔离依据。

---

## 2. 方案选型结论

| 方案 | 摘要 | 取舍 |
| --- | --- | --- |
| **方案 1（推荐）** | 单集群 + 请求级 `TenantContext` + 数据访问层统一收口 | 与现有架构最贴合；依赖工程纪律与测试门禁 |
| **方案 2（可选硬化）** | 共享 Postgres，`schema-per-tenant` | 降低漏写租户条件概率；迁移与连接池复杂度高 |
| **方案 3** | 控制面/数据面拆分 + 内部短期令牌 | 边界最清晰；改动面与链路成本大 |

**本期主线**：方案 1。若审计发现高风险集中区，可 **局部** 引入方案 2，而非一次性全量 schema-per-tenant。

## 4. 身份、成员关系与租户上下文

### 4.1 JWT 校验（第一道门）

- 校验：JWKS 验签、`iss` 白名单、`aud`（或等价受众）、`exp`/`nbf`、时钟偏移容忍。  
- 主体：以 **`sub`**（或 IdP 稳定主键）作为全局用户标识，写入审计与日志。

### 4.2 租户成员校验（第二道门）

- 从 JWT 读取 **租户候选** claim（名称应 **配置化**，例如 `tid` / `tenant_id` / `org_id`）。  
- 查询权威表 **`membership_active(user_sub, tenant_id)`**；不通过则 **403**。  
- **控制面最小模型**：`tenants`；`tenant_members`（`user_sub`、`tenant_id`、角色、启用状态、时间戳）。  
- **缓存**：成员关系可带 TTL 缓存；踢人/撤销必须定义 **可接受的生效延迟**（秒级 vs 分钟级），并通过版本号/失效/短 TTL 实现。

### 4.3 `TenantContext` 与传播

- 字段建议：`tenant_id`、`user_sub`、可选 `roles`、`request_id`/`trace_id`。  
- 绑定方式： **`contextvars`**（或框架等价物）绑定到当前异步任务。  
- **禁止**将客户端请求体中的 `tenant_id` 作为权威来源；若携带，仅允许与上下文 **一致性校验**。  
- **后台任务**：入队快照上下文，worker 恢复；禁止无租户上下文的“全局清扫”误扫全租。  
- **多进程**：Gateway 与 LangGraph 分离时，使用 **内网 + mTLS 或短期内部令牌**（绑定 `tenant_id` 与 `sub`）。

## 5. 数据面：命名空间与访问收口

### 5.1 自有 SQL 表

- 业务表统一 **`tenant_id` NOT NULL**。  
- 唯一约束与主键策略：优先 **`(tenant_id, …)`** 组合，避免跨租 ID 空间合并。  
- 所有读写必须带 **`tenant_id = current_tenant`**；子表 `tenant_id` 与父表一致。

### 5.2 LangGraph checkpoint 与 Store

- **原则**：持久化键空间 **按租户分区**。  
- **推荐**：对外 `thread_id` 可为 UUID；持久化层维护 **`(tenant_id, thread_id)`** 映射或等价内部命名空间；任何列表/恢复/删除先校验归属。  
- **全局单例风险**：当前形态下若存在进程级单例 store/checkpointer，SaaS 模式必须改为 **按租户命名空间包装** 或 **按租户工厂化后端**；禁止无租户边界的共享写入面。

### 5.3 记忆体、向量与缓存

- 集合/namespace/key **从 `TenantContext` 派生**；不接受客户端任意指定 namespace 作为权威。

### 5.4 Artifacts、上传、沙箱

- **`TENANT_ROOT/<tenant_id>/...`**；对象存储 **`…/<tenant_id>/...`**。  
- 访问前 **realpath 规范化**，拒绝 `..`、软链逃逸、非法绝对路径。  
- 建议线程子目录：`threads/<thread_id>/`，且访问前校验 **thread 归属当前租户**。

### 5.5 配置与密钥

- **默认**：租户级密钥与扩展配置存 **加密存储**，仅在成员校验通过且处于该租户上下文时解密使用。  
- **平台级共享配置**仅用于与租户无关的公共能力，不承载租户私密凭据。

### 5.6 兼容与迁移

- 保留 **单租户/私有化** 模式（或 `default` 租户）以兼容社区部署。  
- SaaS 开启后 **强制认证 + 强制租户上下文**；存量数据必须 **回填 `tenant_id` 或冻结**，禁止长期半租户化。

## 6. 审计、观测、测试与上线

### 6.1 审计

每条至少：`tenant_id`、`user_sub`、`request_id`/`trace_id`、动作、资源类型与 id（或哈希）、结果分类；避免记录完整 JWT、明文密钥与未脱敏 PII。

### 6.2 指标与配额

按租户聚合 QPS、token、存储、线程数、错误率；昂贵路径 **429** 与可解释重试提示（实现细节见实现计划）。

### 6.3 测试门禁（必自动化）

- 跨租户负例：用户无权访问租户 B 时，携带租户 A 合法资源 id 在 B 上下文 **不得泄露数据**（对外建议统一 **404**，审计记录真实原因）。  
- 路径逃逸用例集。  
- 成员关系变更与缓存：按目标延迟设计断言。

### 6.4 错误语义（建议统一）

- **401**：未认证或 token 无效。  
- **403**：已认证但 **非租户成员** 或权限不足。  
- **404**：资源不存在，或 **存在但不属于当前租户**（客户端统一为未找到；服务端审计区分）。

### 6.5 上线阶段

- 阶段 0：私有化单租户。  
- 阶段 1：新数据全量 tenant 化；旧数据迁移或冻结。  
- 阶段 2：默认强制认证与租户上下文；关闭匿名入口。  
- checkpoint/store 迁移需 **单独演练与回滚预案**。

---

## 7. 风险与后续可选硬化

- **应用层隔离**依赖持续代码审查与测试；可选 **局部 RLS** 或 **schema-per-tenant** 作为后续硬化项。  
- **LangGraph 上游版本**对存储抽象的约束可能影响“包装器 vs 多实例”选择，应在实现计划中做 **SPIKE** 验证后再冻结接口。
