# 企业级 IM 多用户数据隔离设计

**状态**: 已评审（与产品/实现方确认的设计输入）  
**日期**: 2026-04-21  
**范围**: 单企业、单机器人部署下，通过平台 **用户 ID** 对 **IM 渠道** 做数据分区；**强独立** 的 per-user SOUL/记忆等；**不**在首版将 Web/直连 API 与企微用户主键统一。

---

## 1. 目标与边界

### 1.1 目标

- 同一套 DeerFlow 部署、同一企微（或其它 IM）机器人下，**不同终端用户**的 **长期记忆、USER 画像、自定义 Agent 的 SOUL 及与其同目录的 per-agent 数据** 等 **完全隔离**。
- 每个 IM 用户的 SOUL 为 **可独立演化** 的副本（初值从模板播种，见 §3.2），**不**与另一用户共享可写内容。

### 1.2 明确不在本设计首版范围

- **多企业 / 多 `corpId` 共实例** 的复合主键（已明确为单企业、单机器人，隔离主键 = 平台用户 ID）。
- **Web 前端 / 非 IM 的 LangGraph、Gateway 直连** 与企微 `userid` 的自动统一身份；首版 these 入口仍用 **未分区** 的现有全局根（与产品确认：仅 IM 走分区）。
- **企微群聊、多发言人** 的 thread/分区细分：不挡本设计落地，记为 **后续单独立项**（避免与当前「单 key = 用户」假设纠缠）。

---

## 2. 数据流与信任边界

### 2.1 可信身份来源

- 分区用的用户 ID **仅** 由 **IM 渠道实现** 从平台载荷解析（企微示例：`from.userid`），写入 `InboundMessage.user_id`（或与之等价的单一规范字段）。
- **禁止** 由终端用户文本、外部 query 参数覆盖该 ID。

### 2.2 贯穿链路

1. **渠道**：构造 `InboundMessage`，保证 `user_id`（及既有 `chat_id` / `topic_id` 语义）稳定。
2. **ChannelManager**：创建/恢复 LangGraph `thread`、发起 `runs` 时，将 IM 用户 ID 写入本次运行的 **metadata / `config.configurable`**（实现阶段固定单一键名，例如 `im_user_id` 或 `data_partition_id`），保证 **同一线程后续 turn** 始终携带同一分区键。
3. **Gateway / 嵌入式运行时**：组装 `RunnableConfig` 时 **透传** 该键；IM 侧命令若触发 Gateway 辅助能力，同一请求上下文须使用同一 ID。
4. **Harness**：解析 `memory.json`、`USER.md`、`agents/.../SOUL.md` 等路径时，优先根据 `configurable` 中的分区键解析 **有效根目录**（§3）；**未设置分区键** 时行为与当前版本一致（全局根）。

### 2.3 并发与一致性

- 分区必须 **按每次 run** 的配置解析，**禁止** 依赖进程级单例路径作为 IM 多用户并发下的唯一依据。
- `ChannelStore` 可继续为全局单文件 JSON；隔离主手段为 **运行时 `base_dir` + configurable 分区键**。映射 key 仍为 `channel:chat_id[:topic_id]`，且条目可继续包含 `user_id` 字段。

---

## 3. 磁盘布局与 SOUL 播种

### 3.1 有效根目录与目录树

- 对 **带 IM 分区键** 的运行，**有效 `base_dir`**：

  `{全局应用根（与 `DEER_FLOW_HOME` 等现有解析一致）}/im_users/{safe_user_id}/`

- `safe_user_id`：经 **固定、可单元测试** 的清洗规则（白名单字符或稳定单向编码二选一，必须在实现与文档中写死）；**禁止** `..` 与路径分隔符混入 segment。
- 该树下 **复用** 现有 `Paths` 相对结构：`memory.json`、`USER.md`、`agents/<name>/`（含 `SOUL.md`、`config.yaml`、`memory.json` 等），仅根从全局换到用户子树。
- **`threads/{thread_id}/`**（含 `user-data`、沙箱可见 workspace 等）置于：

  `im_users/{safe_user_id}/threads/{thread_id}/...`

  避免跨用户误配时落到同一磁盘路径。

### 3.2 强独立 SOUL 的初值（模板播种）

- 当某用户子树下 **尚不存在** 目标 `agents/<name>/`（或缺少 `SOUL.md` / 约定种子文件）时，**首次**从 **只读模板** 复制或生成；模板来源默认可为部署内现有全局 `agents/<name>/`，或配置项指定的专用模板目录（实现计划二选一并配置化）。
- 播种 **仅创建该用户目录下的副本**；之后读写 **仅** 用户子树，**不** 写回全局模板。

### 3.3 未分区行为

- 无分区键的请求：**保持** 当前全局 `base_dir` 与 `threads/...` 布局（Web 与存量行为）。

## 4. 失败策略、配置、测试与迁移

### 4.1 失败与安全

- **分区键缺失**：在 **应分区** 的链路中若无法得到合法 `user_id` / `safe_user_id`，须 **失败可见**（记录日志 + 对用户可理解的错误），**禁止** 静默回落到全局根。
- **清洗冲突**：若存在不同原始 ID 映射到同一 `safe_user_id` 的风险，采用 **显式哈希或命名空间** 并在规范中保证碰撞概率可接受或可检测。

### 4.2 配置项（命名在实现阶段最终确定）

- IM 用户数据子树功能 **总开关**。
- `im_users` 段目录名是否可覆盖（可选；默认可固定以满足 YAGNI）。
- SOUL / Agent **模板源**（全局 `agents/` vs 专用模板目录）。
- **`DEER_FLOW_HOST_BASE_DIR`**：与宿主挂载一致推导用户子树，避免 Docker 内外路径错位。

### 4.3 测试要点

- 同 `thread_id`、不同 `im_user_id`：`memory` / SOUL 解析路径必须落在 **不同** 用户子树。
- 不传分区键：与当前版本路径行为 **一致**（回归）。
- 并发交错请求：无交叉写入错误用户目录。

### 4.4 迁移

- **既有全局数据**：默认策略在产品/运维层面明确——例如「上线后 IM 用户从新子树开始」，或「可选一次性迁移脚本」；**不在无运维决策前自动静默搬迁**。

---

## 5. 方案回顾（摘要）

| 路线 | 说明 |
|------|------|
| **推荐：用户子树 + 模板播种** | 每 IM 用户独立 `im_users/<safe>/` 镜像现有 Paths；首次从模板复制 SOUL/agent 文件；与现有代码路径模型一致、可备份。 |
| 集中式存储 | 记忆/SOUL 全部进 DB/桶：扩展性好但与本仓库当前文件心智冲突大，**不作首版默认**。 |
